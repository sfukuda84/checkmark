# speckit-review スキル（2 軸コードレビュー＆品質保証ガイド）

本スキルは、Claude Code における高品質なコードレビューの思想に基づき、対象の変更差分を **2 つの独立した評価軸（Standards 軸 と Spec 軸）** で厳密に検証・修正するエージェントネイティブなレビューガイドラインです。

外部 CLI コマンドに依存せず、エージェント自身のコード探索・分析機能とテスト実行ツールを用いて完結します。

---

## 1. 2 つのレビュー評価軸（Two-Axis Review）

コードが一方の軸を満たしていても、もう一方の軸で破綻しているケース（「規約には従っているが仕様と違う」「仕様通りだが脆弱で保守不能」）を防ぐため、常に 2 軸を独立して評価します。

### 【軸 A: Standards（規約・品質・セキュリティ・パフォーマンス）】
- **セキュリティ脆弱性**:
  - SQL / NoSQL インジェクション（生クエリやパラメータ不備）
  - 認証・認可の境界検証（未認証アクセス、IDOR、ロール偽装）
  - 機密情報（APIキー、シークレット）の混入
  - 入力値バリデーション・サニタイズ漏れ
- **パフォーマンス・スケーラビリティ**:
  - N+1 クエリ、非効率なループ内 DB アクセス
  - インデックスの活用（検索・結合・空間検索などの条件がインデックスに乗るか。使っている DB に合わせて確認する）
  - 不要な全件フェッチ、メモリリーク、不要な再レンダリング
- **型安全性・コード品質**:
  - 型の安全性（`docs/architecture.md` の言語に合わせる。例: TypeScript の `any` の乱用、Python の型ヒントの欠落）
  - エラーハンドリングの網羅性（Promise catch 漏れ、例外の握りつぶし防止）
  - DRY 原則、単一責任の原則
- **コードの匂い（Fowler Code Smells）**:
  - **Duplicated Code**: 同じロジックの重複
  - **Feature Envy**: 他のオブジェクトやテーブルの責務に過剰に立ち入る処理
  - **Data Clumps / Primitive Obsession**: ドメイン概念（UUID、座標、クーポンコード等）の生プリミティブ乱用
  - **Speculative Generality**: 現状の仕様にない不要な先回り・過度な抽象化

### 【軸 B: Spec（仕様・受入基準・設計整合性）】
- **機能要件の充足度**:
  - `specs/<FEATURE>/spec.md` の機能要件（FR-xxx）およびユーザーストーリーの受入基準を満たしているか？
  - 実装漏れ（Missing requirements）やエッジケースの放置がないか？
- **スコープクリープの排除**:
  - 仕様に合意されていない余計な機能・挙動が勝手に混入していないか？
- **アーキテクチャ・憲章整合性**:
  - `specs/<FEATURE>/plan.md`、`data-model.md`、`contracts/*` の設計契約に忠実か？
  - プロジェクト憲章（`.specify/memory/constitution.md`）の原則に準拠しているか？

## 2. レビュー対象の特定（Diff Resolution）

ユーザー入力または実行コンテキストから対象差分を特定します：

| 指定パターン | 差分コマンド | 主な用途 |
|---|---|---|
| **直近のコミット** | `git diff HEAD~1` | ステップ 8 の実装コミット直後のレビュー |
| **ブランチ全体** | `git diff main...HEAD` | フィーチャーブランチと main との全体差分レビュー（既定のブランチが main 以外なら、その名前に読み替える） |
| **未コミット変更** | `git diff` または `git diff --cached` | 作業ツリーの変更差分レビュー |
| **ファイル・パス指定** | `git diff <path>` | 特定ファイル・モジュールに絞ったレビュー |
| **引数なし** | ブランチ差分があれば `main...HEAD`、なければ `HEAD~1` | 自動判別 |

## 2.1 予算と打ち切り

指摘の対応に際限がなくならないように、審査する軸と観点、直す指摘の数、レビューの回数に予算を設ける。品質を下げるためではなく、重要な指摘に時間を使うためである。`speckit-coding` の S10・S11 では必ずこの規則に従う。単独で呼ばれたときも同じ規則を使う（フィーチャーが決まらないときは、backlog に送る代わりにレポートに残す）。

### 軸と観点の選び方

2 軸は「規約・品質」と「仕様」という独立した見方であり、どちらかが不要になる変更は少ない。そのため、軸は原則として省かない。省くのは次の場合だけで、差分から機械的に決め、レポートの「予算」の節に省いた軸と観点、その理由を書く。

| 条件（差分から判定する） | 扱い |
|---|---|
| ドキュメントだけの変更（実行されるコード、設定、スキーマ、テストに差分がない） | Spec 軸だけを見る。Standards 軸は、秘密情報の混入だけを確かめる |
| フィーチャーに属さない変更（依存関係の更新、設定、CI など。`specs/` の対象がない） | Spec 軸は、憲章と `docs/architecture.md`・`docs/nfr.md` との整合だけを見る |
| DB アクセス・クエリ・スキーマの差分がない | Standards 軸の N+1、インデックス、不要な全件フェッチの観点を省く |
| 画面の差分がない（`ui.md` が「UI なし」、または S4-1 を省いた） | Spec 軸の `ui.md`・トークン・アクセシビリティの観点を省く |
| それ以外 | 2 軸のすべての観点を見る |

- 機能の重さ（`speckit-worktree` §2「機能の重さ」）が `重` のときは、軸も観点も省かない。
- セキュリティの観点（インジェクション、認証と認可、秘密情報、入力の検証）は、ドキュメントだけの変更を除いて省かない。

### 直す指摘の数

指摘は軸ごとに数える。

- **1 軸の指摘が 15 件以下**: LOW も含めて全件を直す。
- **1 軸の指摘が 15 件を超える**: CRITICAL・HIGH・MEDIUM は件数に関わらず全件を直す。LOW は直さず、`specs/<FEATURE>/reviews/backlog.md`（様式: [templates/backlog.md](templates/backlog.md)）に 1 行ずつ送る。レポートには、送った件数と backlog.md のパスだけを書く。
- backlog.md は追記していく。後の機能で同じ箇所に触れるときや、まとめて片付けるときに拾い、片付けた行の「状態」を「済（<コミット>）」にする。`speckit-converge`・`speckit-analyze` は、backlog.md の行を実装漏れとして扱わない。
- 直し方に判断が要る指摘（リファクタリングの方針の分岐など）は、推奨案で直して `decisions.md` に記録する（`speckit-worktree` §4「質問はまとめる」）。

### 回数と打ち切り

回数は機能の重さで決まる（軽は S10 の 1 回、標準と重は S10・S11 の 2 回）。

- **2 回目（S11）で CRITICAL・HIGH が 0 件**: 残りの指摘を上の数の規則で直し、テストを通して S11 を記録する。3 回目は行わない。
- **2 回目（S11）で CRITICAL か HIGH が残った**: 直したうえで、直した差分だけを、その指摘が出た軸でもう一度確かめてから S11 を記録する。この確かめでも CRITICAL か HIGH が残るときは、そこで止めてユーザーに判断を求める（自動モードでも止まる）。
- **1 回だけの機能（軽）で、S10 に CRITICAL か HIGH があった**: 直した差分だけを、その軸でもう一度確かめてから S10 を記録する。残るときは、上と同じく止めて聞く。

## 3. レビューの実行手順

1. **差分とコンテキストのロード**:
   - `git diff <range>` を取得し、変更されたファイル一覧・行を把握。
   - 関連ドキュメント（`specs/<FEATURE>/spec.md`, `plan.md`, `constitution.md`）を読み込む。
2. **Standards 軸 ＆ Spec 軸の精査**:
   - 各ファイルの変更行（および周辺コンテキスト）を読み、上記 2 軸の観点で問題点を抽出。
   - 問題ごとに重大度（**CRITICAL**, **HIGH**, **MEDIUM**, **LOW**）を割り当て。
3. **レビューレポートの出力**:
   - 以下の Markdown フォーマットで報告。`speckit-coding` の S10・S11 では、`specs/<FEATURE>/reviews/review-<回>.md` にも保存する（同じ回のファイルがあれば追記する）。2 回目の審査と完了報告は、このファイルを読む。

```markdown
# コードレビュー結果報告（Code Review Report）

## レビュー対象
- **差分範囲**: `git diff <range>` (X files changed, +Y / -Z lines)
- **仕様ドキュメント**: `specs/<FEATURE>/spec.md`

## 予算
- **軸と観点**: 2 軸（省いた観点: なし / <観点>: <理由>）
- **直した指摘**: Standards X 件 / Spec Y 件（LOW を backlog に送った件数: Z 件 → `specs/<FEATURE>/reviews/backlog.md`）
- **審査の方法**: サブエージェントによる独立審査（軸ごと） / 親による順次審査

## 課題サマリー
- **CRITICAL**: X 件（セキュリティ脆弱性、憲章違反、仕様未達）
- **HIGH**: Y 件（性能問題、重大な型不整合、エッジケース未考慮）
- **MEDIUM**: Z 件（コードの匂い、リファクタリング推奨）
- **LOW**: W 件（軽微な改善提案）

---

### 【Standards（規約・品質・セキュリティ・パフォーマンス）】

#### R<回>-S<nn>: [CRITICAL/HIGH/MEDIUM/LOW] [カテゴリ] 課題タイトル
- **対象箇所**: [`src/path/to/file.ts#L25-L35`](file:///absolute/path/to/file.ts#L25-L35)
- **問題の説明**: 何がなぜ問題なのか、発生しうるリスク。
- **採否**: 採用 / 不採用（理由） / backlog
- **改善コード案**:
```typescript
// 修正後コード
```

---

### 【Spec（仕様・受入基準整合性）】

#### R<回>-P<nn>: [CRITICAL/HIGH/MEDIUM/LOW] 要件との乖離・不足
- **対象要件**: FR-002 / User Story 1 受入基準
- **採否**: 採用 / 不採用（理由） / backlog
- **現状の実装**: ...
- **求められる挙動**: ...
- **推奨対応**: ...
```

### 3.1 独立審査（サブエージェント）

サブエージェント（Claude Code の Agent など）が使えるときは、軸ごとに 1 つずつ、**会話の文脈を持たない**サブエージェントに審査させる。実装した本人の思い込みを持ち込まないためである。

- **渡すもの**: 軸の名前と §1 のその軸の観点、差分の範囲（コマンド）、読むべき文書のパス、§2.1 で省いた観点、出力の形式（上のレポートの指摘の形。1 軸 15 件を超えたら LOW は 1 行ずつ）。依頼文の雛形は `speckit-worktree` の [references/delegation.md](../speckit-worktree/references/delegation.md) にある。「落とす理由を探す」立場で審査させ、指摘ごとに根拠（ファイルと行、文書の該当箇所）を必ず付けさせる。
- **渡さないもの**: 実装の経緯、親の判断、「たぶん問題ない」といった見立て。
- Standards 軸と Spec 軸は並行に走らせてよい。
- **2 回目のレンズ**: 1 回目の指摘を直した差分を中心に、修正による副作用と退行を重点にする。1 回目の記録（`review-1.md`）を渡し、同じ指摘の繰り返しではなく、直し方の妥当性も確かめさせる。
- サブエージェントが使えない環境では、親が軸を 1 つずつ、軸を切り替えるたびに観点を読み直して審査する。

### 3.2 裏取りと採否

親は、サブエージェントの指摘をそのまま直さない。指摘ごとに次を行う。

1. 根拠のファイルと行、文書の箇所を自分で開いて確かめる。再現できるものは、テストで再現する。
2. 採否を決める: **採用**（直す）、**不採用**（理由: 誤読、仕様で許されている、根拠がない など）、**backlog**（§2.1 で 1 軸 15 件を超えた LOW）。仕様や憲章を変える必要があるものは、まとめてユーザーに聞く（自動モードでは止まる）。
3. 採否と理由をレポートに残す。不採用の指摘も消さない。
4. 修正は担当（サブエージェント）に任せてよい（`speckit-worktree` §4「親と担当の役割」）。修正の後、親がテストを再実行する。

## 4. 指摘事項の修正（Remediation）と対話

1. **優先対応**:
   - **CRITICAL / HIGH** の指摘から順に修正コードを適用します。直す範囲は §2.1「直す指摘の数」に従います（1 軸 15 件以下なら LOW も含めて全件、超えたら LOW を backlog へ）。
2. **対話的確認**:
   - リファクタリングの方針に複数の選択肢がある場合や、仕様の解釈・設計トレードオフについて判断が必要な場合は、推奨案（`**Recommended:**`）で直して `decisions.md` に記録します（`speckit-worktree` §4「質問はまとめる」）。仕様や憲章を変える必要があるときだけ、ユーザーに質問して合意を得てから修正します。単独で呼ばれたとき（フィーチャーの工程の外）は、推奨案を添えて質問し、合意を得てから修正します。
3. **テスト検証**:
   - 修正適用後、必ずテストコマンド（例: `npm test`）を実行し、すべてのテストが PASS すること（リグレッションがないこと）を確認します。
