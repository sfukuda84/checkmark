# speckit-design スキル（デザインの要件 → docs/design/ ＋ 機能ごとの ui.md）

デザインの要件を、性質の違う 2 つに分けて書く。

| 出力 | 中身 | 作るとき | 使われ方 |
|---|---|---|---|
| `docs/design/DESIGN.md` | **見た目**の共通の決め事（ブランドとトーン、色、文字、レイアウトと余白、形と奥行き、コンポーネント、してよいこと・してはいけないこと） | 立ち上げ（`speckit-bootstrap` の B5-1）か、このスキルの単独実行 | 憲章から参照され、各機能の `ui.md` と `plan.md` が従う |
| `docs/design/EXPERIENCE.md` | **振る舞い**の共通の決め事（情報設計、画面一覧、画面遷移、状態のパターン、言葉づかい、アクセシビリティ） | 同上 | 同上 |
| `docs/design/tokens.tokens.json` | 色、文字、余白、角丸などの**値の正本**（DTCG 2025.10）。テーマは `tokens.<テーマ>.tokens.json` | 同上 | 実装はトークンから値を使う |
| `specs/<NNN-name>/ui.md` | **機能ごとの画面仕様**（画面と要件の対応、画面ごとの表示・操作・入力・状態、文言） | `speckit-feature` の S4-1（§3） | `plan.md`、`tasks.md`、実装、レビューが参照する |

この文書は正本をツールに依存しない Markdown と JSON で持つ。Claude Design は、案を見比べて選ぶための任意の道具として使い（§4）、そこで決めたことは必ず正本に書き戻す。

## 0. 大原則

- **正本は `docs/design/` と `ui.md` である。** Claude Design のアーティファクトは参照先として URL を残すだけにし、値や仕様の正本にしない。
- **値はトークンにだけ書く。** `DESIGN.md` と `ui.md` には色や大きさの値を書かず、トークン名（`color.brand.primary` など）で参照する。
- **技術を書かない。** フレームワークやコンポーネントのライブラリは `docs/architecture.md` と各機能の `plan.md` で決める。ここでは「何を、どう見せ、どう振る舞うか」を書く。
- **アクセシビリティの水準は `docs/nfr.md` に従う。** `NFR-UX` の水準（例: WCAG 2.2 AA）を `EXPERIENCE.md` の最低線にする。違う水準が要る場合は、`speckit-nfr-feature` の更新モードで先に見直す。
- **推測で埋めない。** ブランドや印象など、利用者しか知らないことは質問する。自動モードでは推奨案を仮定として採用し、記録する（§6）。
- **書き出す前に合意を取る。**
- ドキュメントは日本語で書く。

## 1. 引数と入出力

```text
$ARGUMENTS
```

| 指定 | 動作 |

| `--auto` | 質問せずに推奨案を採用して進める（§6）。`speckit-bootstrap` の自動モードと一括質問モードからは、このモードで呼ばれる |

| `docs/nfr.md` | `NFR-UX`（対応するブラウザと端末、アクセシビリティの水準）、`NFR-PE`（画面の応答時間） |

`docs/design/` がすでにある場合は、**更新モード**として §5 に従う。

## 2. 共通の決め事を作る（立ち上げ、単独実行）

### ステップ 1: 読み込みと対象の判定

入力を読み、次を整理する。

- **画面の有無**: `docs/architecture.md` に利用者向けの画面（Web、モバイル、デスクトップ、管理画面）がなく、CLI や API だけのサービスなら、ステップ 5 で `DESIGN.md` を「**対象**: UI なし」として理由だけを書き、ステップ 7 と 8 だけを行って終える（憲章への条項は足さない）。`EXPERIENCE.md` とトークンは作らない。
- **利用者と場面**: ロール、使う端末、使う状況（外出先で片手で、事務所の PC で長時間、など）
- **画面の候補**: 各機能の主な要求から、主な画面を拾う（例: 予約の一覧、予約の登録）。共通の画面は 000 から拾う。
- **決まっていること**: `NFR-UX` の水準と対応する端末、000 の多言語やダークモードの扱い

### ステップ 2: ヒアリング

次の論点のうち、入力から決まらないものを AskUserQuestion で聞く。1 ラウンド最大 4 問、推奨案を先頭に置く。

| 順 | 論点 | 書く場所 |
|---|---|---|
| 1 | 利用者に与えたい印象（3 語以内）と、参考にしたい・したくないサービス | `DESIGN.md` の「ブランドとトーン」 |
| 2 | ブランドの素材（ロゴ、決まった色、既存のブランドガイド）の有無 | 同上、トークンの `color.brand` |
| 3 | 主に想定する端末（スマートフォン中心か、PC 中心か） | 「レイアウトと余白」、`EXPERIENCE.md` の「情報設計」 |
| 4 | テーマ（ライトのみ / ライトとダーク） | 「色」、`tokens.dark.tokens.json` |
| 5 | 文体と呼びかけ（です・ます調など） | `EXPERIENCE.md` の「言葉づかい」 |
| 6 | 対応する言語 | 「文字」の「多言語」 |

推奨案は、入力から判断できる最も無難な案にする。例えば、業務用で PC 中心なら「落ち着いた、情報が多くても読みやすい」、テーマは「ライトのみ（ダークは後で足せる）」。

`--with-mock` のときは、ヒアリングの後に §4 の手順で案を作り、選んでもらってからステップ 3 に進む。

### ステップ 3: 画面一覧と情報設計の整理

- 主な画面に ID を振る。形は `SCR-<機能番号 3 桁>-<連番 2 桁>` で、機能番号は `docs/feature/` のファイル名の先頭の番号である（例: `001-reservation.md` の最初の画面は `SCR-001-01`）。機能をまたいで ID が重ならないので、機能を並行して仕様化しても ID は衝突しない（同じ文書の近くの行を変えると、マージで競合することはある）。
- 状態は「構想」にする。画面の詳細は、各機能の S4-1（§3）で `ui.md` に書き、そのときに「仕様化済み」にする。
- 主なナビゲーションと、ロールごとに見える範囲を決める。

### ステップ 4: 書き出し案の提示と合意

次をまとめて提示し、承認を得る。

1. ブランドとトーン、主要な色と文字の方針（`--with-mock` なら、選んだ案）
2. 画面一覧（ID、画面、機能、ロール）と主なナビゲーション
3. 状態のパターン、言葉づかい、アクセシビリティの最低線
4. 憲章に足す条項（ステップ 6）

### ステップ 5: 書き出し

- `docs/design/DESIGN.md`、`EXPERIENCE.md`、`tokens.tokens.json` を、それぞれのテンプレートに沿って書く。テンプレートの例の値は、決めた内容に置き換える。
- トークンは DTCG 2025.10 の形で書く。
  - 色は `{"colorSpace": "srgb", "components": [r, g, b], "hex": "#rrggbb"}`、大きさは `{"value": 数値, "unit": "px"}`（または `rem`）にする。
  - 役割のトークン（`color.action.primary` など）は、基本の色を `{color.brand.primary}` の形で参照する。
  - ダークなどのテーマは `tokens.<テーマ>.tokens.json` に、基本のファイルにあるトークンの上書きだけを書く。
- 本文の文字と背景のコントラストが、アクセシビリティの水準（AA なら 4.5:1）を満たす色にする。組み合わせと比を `DESIGN.md` の「色」に書く。

### ステップ 6: 憲章への反映

憲章に `docs/design/` を参照する条項がなければ、`speckit-constitution` の手順で改訂として足す（版を上げ、同期影響レポートを更新する）。条項の例:

- 画面を持つ機能は、`docs/design/DESIGN.md` と `EXPERIENCE.md` に従い、画面仕様（`specs/<NNN-name>/ui.md`）を `plan.md` より先に作る。この条項を足す前に仕様化した機能には、さかのぼって求めない。
- 色、文字、余白などの値は `docs/design/` のトークンから使い、実装に値を直接書かない。
- アクセシビリティは `docs/nfr.md` の `NFR-UX` の水準を満たし、`plan.md` の憲章チェックで確かめる。

「UI なし」のときは、条項を足さない。

### ステップ 7: 検証

```bash
python3 <skills>/speckit-design/scripts/validate_design.py docs/design
```

`<skills>` は、このスキルが置かれた skills ディレクトリである。`python3` がない環境では `python` または `py -3` に読み替える。エラーが 0 件になるまで直す。

### ステップ 8: 報告

- 作成したファイルと、画面一覧の件数（機能ごと）
- ブランドとトーン、テーマ、主に想定する端末、アクセシビリティの水準
- `--with-mock` のとき: モックの URL、採用した案と理由。モックを作れなかったときは、その理由
- 憲章に足した条項
- 次の手順の案内（`speckit-bootstrap` の中で実行している場合は、その手順に戻る。単独なら `speckit-all` で各機能の仕様化へ）。共通基盤（000）を実装した後に、Claude Code の `/design-sync` で実際のコンポーネントを Claude Design に取り込めること（§4「実装した後」）

## 3. 機能ごとの画面仕様（`speckit-feature` の S4-1）

`speckit-feature` の S4-1 から、`WORKTREE_DIR` の中で実行する。`FEATURE_DIR` は `specs/<FEATURE_NAME>` である。

1. **対象の判定**: 次のどれかなら、`FEATURE_DIR/ui.md` を「**対象**: UI なし」にして理由を 1 行書き、手順 5 に進む。
   - `docs/design/DESIGN.md` が「UI なし」
   - この機能の要件（`spec.md` の FR）に、利用者が見る画面がない（バッチ処理、外部 API だけ、など）

   `docs/design/` がない（デザインの工程を足す前に立ち上げた）プロジェクトで、画面のある機能は、`ui.md` を「UI あり」のまま、共通の決め事を参照せずに書く（使うコンポーネントは一般的な名前で書く）。完了報告で、`speckit-design` を単独で実行して共通の決め事を作ることを案内する。
2. **下書き**: [templates/ui.md](./templates/ui.md) に沿って、`spec.md` のユーザーストーリーと要件から画面を起こす。
   - 画面 ID は `SCR-<この機能の番号>-<連番>` にする。`EXPERIENCE.md` の画面一覧にこの機能の画面が「構想」として挙がっていれば、その ID を使う。
   - 各画面の「対応する要件」に FR の番号を書く。画面を伴う FR は、どれかの画面に対応させる。
   - 表示、操作、入力と検証、状態、使うコンポーネント、端末による違い、アクセシビリティを書く。共通の決め事（`DESIGN.md`、`EXPERIENCE.md`）と同じことは書かず、違う点だけを書く。
3. **確認**: 画面の構成や、要件の読み方で判断が要る点を、推奨案を添えて質問する（最大 3 問）。`--auto` なら推奨案を採用し、`FEATURE_DIR/auto-decisions.md` に記録する。
   - `--with-mock` のときは、ここで §4 の手順で主な画面のモックを作り、案を選んでもらう。選んだ案の URL を `ui.md` のヘッダの「モック」に書き、案から決まったことを本文に反映する。
4. **反映**:
   - 画面を作るうえで `spec.md` の要件の不足や矛盾に気づいたら、`spec.md` も直す（`## Clarifications` に `### Session YYYY-MM-DD (UI)` として記録する）。
   - `docs/design/EXPERIENCE.md` の画面一覧で、この機能の行を足すか直し、状態を「仕様化済み」にする。ほかの機能の行、「最終更新」、「変更履歴」は変えない（機能どうしのマージの競合を減らすため）。
   - 新しい共通のコンポーネントや状態のパターンが要る場合は、`DESIGN.md` か `EXPERIENCE.md` に足し、「変更履歴」に書く。トークンの追加も同じにする。既存のトークンや決め事を変える必要がある場合は、自動では変えず、ユーザーに確認する（自動モードでは止まる。§6）。
5. **検証**:

   ```bash
   python3 <skills>/speckit-design/scripts/validate_design.py docs/design --feature specs/<FEATURE_NAME>
   ```

   エラーが 0 件になるまで直す。警告（画面に対応しない FR など）は、画面を伴わない要件なら残してよい。`docs/design/` がない場合の警告も残してよい。

6. `speckit-feature` に戻り、`checkpoint <FEATURE_NAME> S4-1` を記録する。

## 4. Claude Design でモックを作る（`--with-mock`）

`--with-mock` のときだけ行う。Claude Design は、案を見比べて選ぶために使う。決めたことは、必ず `docs/design/` か `ui.md` に書き戻す。

### 使えるかどうかの判定

次をすべて満たすときに使う。満たさないときは、モックを作らずにテキストの仕様だけで進め、理由を完了報告と `DESIGN.md` の「参照したモック」（機能では `ui.md` のヘッダ）に書く。止まらない。

- Claude Code で動いている（ほかのエージェントには `/design` がない）
- `/design` を使える（アーティファクトを公開でき、アカウントで Design のテンプレートが使える）。呼び出してエラーになったら、使えないものとして扱う
- Claude Code のクラウドセッション（`CLAUDE_CODE_REMOTE=true`）では、`/design` が使えないことがある。試してエラーになったら、テキストの仕様で進める

Claude Design は Claude の通常の利用枠を使い、消費が大きい。モックは、立ち上げでは 1 つの代表の画面、機能では主な画面 1〜2 枚に絞る。

### 立ち上げ（§2 ステップ 2 の後）

1. ヒアリングの結果から、代表の画面（最もよく使う画面）を 1 つ選ぶ。
2. `/design` に次の依頼文を渡し、方向性の違う案を 2〜3 個、1 つのキャンバスに並べて作る。
   - サービスの概要、利用者と場面、与えたい印象、参考にするサービス、主に想定する端末、テーマ
   - 画面の目的と、表示する主な情報（ダミーのデータでよい）
   - 案ごとの違い（例: 案 A は情報を詰める、案 B は余白を広く取る）
3. 公開された URL を示し、AskUserQuestion で案を選んでもらう（推奨案を先頭に置く）。選んだ案に直したい点があれば、`/design` で直してから次に進む。
4. 選んだ案から、色、文字、余白、角丸、コンポーネントの形を読み取り、トークンと `DESIGN.md` に書き戻す。`DESIGN.md` の「参照したモック」に、URL、採用した案、採用しなかった案と理由を書く。

### 機能（§3 手順 3）

1. `ui.md` の下書きから、主な画面を 1〜2 枚選ぶ。
2. `/design` に、`ui.md` の該当する画面の仕様と、`docs/design/DESIGN.md` の決め事（印象、主要な色、文字、コンポーネント）を渡して作る。案は 1〜2 個にする。
3. URL を示し、採用する案と直す点を確認する。選んだ案の URL を `ui.md` のヘッダの「モック」に書き、決まったことを本文に反映する。

### 実装した後

- 共通基盤（000）などで、実際のコンポーネントができた後は、Claude Code の `/design-sync` で Claude Design に取り込める。以後のモックは実際のコンポーネントで作られる。公式の説明では、取り込めるのは React のデザインシステムである。`docs/architecture.md` のフロントエンドが React でなければ、取り込みは案内しない。
- `/design-sync` はユーザーが始めるコマンドである。このスキルからは実行せず、完了報告で案内する。取り込みには `/design-login` での認可が要り、大きなリポジトリでは初回に数時間かかる。

## 5. 更新モード

- `docs/design/` を変えるときは、差分と影響（すでに `ui.md` を作った機能、実装済みの機能で変わること）を示し、合意した変更だけを反映する。各文書の「変更履歴」に日付、内容、理由を足す。
- トークンの名前は変えない（実装が参照している）。役割が変わった場合は新しい名前を足し、古い名前に `$deprecated` を付ける。
- 機能の `ui.md` は、その機能の仕様工程（`speckit-feature`）の中で直す。マージ済みの機能の画面を変える場合は、その機能の `spec.md` と `ui.md` を直す変更として扱う。

## 6. 自動モード（`--auto`）

| 論点 | 自動モードでの動作 |
|---|---|
| §2 のヒアリング | 入力から推奨案を作って採用する。根拠がなければ、落ち着いた印象、入力から判断できる主な端末、ライトのみ、です・ます調、日本語のみ、を採る |
| §2 の書き出し案の合意 | 提示せずにそのまま書き出す。内容は完了報告に載せる |
| §3 の確認 | 推奨案を採用する |
| §4 の案の選択 | 推奨案（入力と最もよく合う案）を採用する。直す点は求めない |
| 既存のトークンや決め事の変更（§3 手順 4） | 自動では変えずに止まる |

- 自動で決めたことは、立ち上げでは `docs/auto-decisions.md` に、機能では `FEATURE_DIR/auto-decisions.md` に記録する（`speckit-bootstrap` §7、`speckit-worktree` §6 の書き方に従う）。ブランドとトーン、主な端末は、見直しの優先度を「高」にする。

## 7. 禁止事項

- `DESIGN.md` や `ui.md` に、色や大きさの値を直接書くこと（トークン名で参照する）
- Claude Design のアーティファクトだけに決めたことを残し、正本に書き戻さないこと
- `ui.md` に技術（フレームワーク、ライブラリ、API のパス）を書くこと
- ユーザーの合意なしに `docs/design/` を書き出す、または上書きすること（自動モードを除く）
- `/design-sync` をユーザーの指示なしに実行すること
