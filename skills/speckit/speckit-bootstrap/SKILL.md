# speckit-bootstrap スキル（新規プロジェクトの立ち上げ: B0 → B6）

コアコンセプトから、仕様化と実装に入れる状態（機能の一覧、アーキテクチャ、憲章、共通基盤、非機能要件、デザインの要件）までを、1 つの流れで作る。各ステップの中身は、それぞれのスキルの SKILL.md に従う。このファイルには順番と引き継ぎだけを書く。

## 1. 引数

```text
$ARGUMENTS
```

引数があれば、コアコンセプトへの追記、または各ステップへの追加の希望として扱う。

`--auto` と `--oneshot` は実行モードの指定であり、位置を問わない。追記や希望として扱う前に取り除く。

| 指定 | モード | 動作 |
|---|---|---|
| なし | 対話 | 各ステップのスキルの手順どおりに、ユーザーに質問しながら進める |
| `--auto` | 自動 | ユーザーに一度も質問せず、推奨案を採用して最後まで進める（§7） |
| `--oneshot` | 一括質問 | B0 で一度だけ、影響の大きい論点をまとめて質問する。以降は `--auto` と同じく自動で進める（§7） |

両方が指定されたときは `--oneshot` として扱う。

`--adopt` は、既存のプロジェクトに scaffold を取り込んだ後（`new-speckit-project adopt`）に使う指定であり、位置を問わない。上のどのモードとも組み合わせられる。付けると、B0 の後に §8 の取り込みの計画を作り、ステップごとに「移し替える / 完了として記録 / 新しく作る / 飛ばす」を決めてから進める。追記や希望として扱う前に取り除く。

`--with-mock` は、B5-1（デザインの要件）で Claude Design のモックを作って案を選ぶ指定である（`speckit-design` §4）。上のどのモードとも組み合わせられ、位置を問わない。追記や希望として扱う前に取り除く。付けなければ、テキストの仕様だけを作る。

## 3. 進捗の記録と再開

- 各ステップが終わったら、次のコマンドで記録する（`git add -A` して、trailer `Speckit-Bootstrap: <ステップ>` 付きでコミットする）。変更がなくても `--allow-empty` で空コミットとして記録する。

  ```bash
  python3 <skills>/speckit-bootstrap/scripts/bootstrap.py checkpoint <ステップ> "<§2 の subject>" --allow-empty \
      [--trailer "Co-Authored-By: …"]
  ```

  `<skills>` は、このスキルが置かれた skills ディレクトリ（`.claude/skills`、`.agents/skills`、`.kiro/skills` のいずれか）である。コミットを手で書かない。git は、メッセージの最後の段落にある trailer しか読まないため、trailer を別の段落に分けると（例: `-m "Speckit-Bootstrap: B1" -m "Co-Authored-By: …"`）完了が数えられない。ほかの trailer を付けるときは `--trailer` で渡すと、同じ最後の段落にまとめられる。

- Claude Code のクラウドセッション（環境変数 `CLAUDE_CODE_REMOTE` が `true`）では、コミットのたびに `git push -u origin HEAD` で作業ブランチを push する。VM が回収されても、完了したステップが残る。push に失敗しても止まらず、失敗したことを完了報告に挙げる。ローカルでは push しない。

- 開始時に、次のコマンドで完了済みのステップ（`COMPLETED_STEPS`）と次のステップ（`NEXT_STEP`。すべて済んでいれば `DONE`）を調べる。

  ```bash
  python3 <skills>/speckit-bootstrap/scripts/bootstrap.py state
  ```

- 完了済みのステップは飛ばし、`NEXT_STEP` から再開する。
- B5-1 は後から足したステップである。B6 まで記録があるのに B5-1 の記録がない（B5-1 を足す前に立ち上げを終えた）プロジェクトでは、`state` は B5-1 を飛ばす（`NEXT_STEP: DONE`）。B5-1 を自動で実行せず、立ち上げは完了として扱い、`speckit-design` を単独で実行すればデザインの要件を足せることを案内する。
- 記録がなくても成果物がそろっているステップ（`--adopt` で取り込んだプロジェクトに多い）は、内容を確かめ、完了として記録してよいかをユーザーに確認する。
- 再開する場合は、完了済みのステップと再開するステップをユーザーに示してから進める。
- 自動モード・一括質問モードでは確認せずに進める。成果物がそろっているステップは、内容を確かめて完了として記録し、再開するステップを示すだけにする。

## 4. 手順

### B0: 事前確認

1. Git リポジトリのルートで、ブランチが `main` であり、未コミットの変更がないことを確かめる。Claude Code のクラウドセッション（`CLAUDE_CODE_REMOTE` が `true`）では、`main` の代わりにセッションの作業ブランチにいればよい（規則は steering の「Claude Code のクラウドセッション」）。満たさない場合は、ユーザーに状況を示して対応を確認する。
2. `docs/concept/` に、`.gitkeep` 以外のコアコンセプトのファイルがあることを確かめる。`--adopt` のときは、ない場合も質問せずに 4 へ進む（既存の README や企画書をコンセプトとして扱い、§8 で `docs/concept/core-concept.md` に移し替える）。ない場合は、サービスのコアコンセプト（誰の、どんな課題を、どう解決するか）を質問し、`docs/concept/core-concept.md` に書いてコミットする。
3. 引数でコンセプトへの追記があれば、`docs/concept/core-concept.md` の末尾に「追記（日付）」の節として足す。
4. `--adopt` のときは、§8 の取り込みの計画を作って合意を得る。`--oneshot` と組み合わせたときは、§7 の一括質問で、既存の資料とコードから決まる論点（使っているクラウド、言語など）を除いて選ぶ。

### B1: コンセプトを機能に仕分ける

`speckit-concept-2-feature` の手順を、新規モードで最後まで行う。ヒアリング、競合調査、分割案の合意、書き出し、検証を省かない。

- 認証やメール送信などの共通機能は機能にせず、`premises.md` の「共通基盤の候補」に記録させる（B4 で使う）。
- 番号 `000` と `999` は使わない（B4 と B5 で使う）。

### B2: アーキテクチャと技術選定

`speckit-architecture` の手順を最後まで行う。ヒアリング、3 系統の比較、案の選択、`docs/architecture.md` の書き出しを省かない。

### B3: 憲章

`speckit-constitution` の手順で `.specify/memory/constitution.md` を作る。原則の案を作るときは、次を入力として渡し、ユーザーの確認を取る。

- 仕様駆動開発と言語のルール（`.kiro/steering/` の各ファイル）
- `docs/architecture.md` の技術スタックと構成。例: 「技術スタックは docs/architecture.md に従う。変える場合は speckit-architecture の見直しを経る」
- 非機能要件の参照。例: 「すべての機能は docs/nfr.md の横断要件を満たし、plan.md の憲章チェックで確かめる」（`docs/nfr.md` は B5 で作る）
- テストの方針（テストファーストにするかなど）は、ユーザーに質問して決める。

### B4: 共通基盤

`speckit-common-feature` の手順を最後まで行い、`docs/feature/000-app-basic.md` を作る。`spec_order.md` の先頭への追加と、各機能の依存の更新まで行う。

### B5: 非機能要件

`speckit-nfr-feature` の手順を最後まで行い、`docs/nfr.md` と `docs/feature/999-app-nfr.md` を作る。憲章に `docs/nfr.md` を参照する条項があることも確かめる。

### B5-1: デザインの要件

`speckit-design` の §2 の手順を最後まで行い、`docs/design/` を作る。引数に `--with-mock` があれば、§4 の手順で Claude Design のモックを作って案を選ぶ。自動モード・一括質問モードでは `--auto` として実行する。憲章に `docs/design/` を参照する条項を足すところまで行う。

### B6: 全体の検証

1. 機能一式を検証し、エラーが 0 件になるまで直す。

   ```bash
   python3 <skills>/speckit-concept-2-feature/scripts/validate.py docs/feature
   ```

   `<skills>` は、このスキルが置かれた skills ディレクトリである。`python3` がない環境では `python` または `py -3` に読み替える。

   デザインの要件も検証し、エラーを 0 件にする。

   ```bash
   python3 <skills>/speckit-design/scripts/validate_design.py docs/design
   ```

2. 次の整合を確かめる。食い違いがあれば、該当するスキルの更新モードで直すか、ユーザーに確認する。
   - `docs/architecture.md` の構成と、`docs/nfr.md` の目標値（構成と費用で達成できるか）
   - 憲章と、`docs/architecture.md`、`docs/nfr.md` の参照
   - `000-app-basic.md` と、`premises.md` の「共通基盤の候補」
   - `spec_order.md` の並び（`000` が先頭、`999` が MVP の最後）
   - `docs/design/EXPERIENCE.md` のアクセシビリティの水準と、`docs/nfr.md` の `NFR-UX`。画面の有無（`DESIGN.md` の「対象」）と、`docs/architecture.md` の構成
   - 憲章と、`docs/design/` の参照
3. 環境と設定を診断し、ERROR を 0 件にする（WARN のうち、開発コマンドがないものは、最初の機能で記録するので残してよい）。

   ```bash
   python3 <skills>/speckit-worktree/scripts/worktree_helper.py doctor
   ```

4. §3 の `bootstrap.py checkpoint B6` で記録する。

  - `speckit-all`（引数なし）で、`000-app-basic` から 1 件ずつ仕様化と実装を進める。画面のモックも作るときは `speckit-all --with-mock`

## 6. 規則

- 各ステップの中身は、それぞれのスキルの SKILL.md に従う。このスキルで手順を省いたり、ヒアリングを飛ばしたりしない。自動モード・一括質問モードでは、ヒアリングや合意の手順を §7 の規則で置き換える（調査、比較、書き出し、検証は省かない）。
- ユーザーが「このステップは後でやる」と明示した場合は、そのステップを飛ばして次に進んでよい。完了報告に、飛ばしたステップと影響を書く。飛ばしたステップは記録しない（再実行時に再開の対象になる）。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。

## 7. 自動モード（`--auto`）と一括質問モード（`--oneshot`）

どちらのモードも、各ステップのスキルでユーザーに聞く論点（ヒアリング、案の選択、書き出し前の合意など）を、エージェント自身が作る推奨案で決めて進める。違いは、最初に一度だけ質問するかどうかである。

立ち上げで決めることは、利用者、MVP の範囲、課金、予算など、ユーザーしか知らない事業の前提を多く含み、後のすべての機能の土台になる。そのため、自動で決めたことは**仮定**として扱い、そうと分かる形で記録して、後から見直せるようにする（下の「記録」）。`speckit-concept-2-feature` の「推測で埋めない」は、このモードに限り「推奨案を仮定として明示して採用し、記録する」に置き換える。

### 一括質問（`--oneshot` の B0）

B0 の 1〜3 の後で、次の候補のうち、コンセプト（`docs/concept/`）と引数から決まらないものを上から順に最大 4 つ選び、AskUserQuestion の 1 回にまとめて質問する。各問には推奨案を先頭に `(Recommended)` 付きで置く。

| 順 | 論点 | 使うステップ |
|---|---|---|
| 1 | MVP 時の月額予算の上限（`speckit-architecture` の A2） | B2、B5 |
| 2 | 使いたい、または避けたいクラウド・SaaS と、得意な言語（A1、A4） | B2 |
| 3 | MVP の範囲（最初に有料提供するまでに要る業務フロー。`premises.md` の P8） | B1 |
| 4 | 課金単位とプランの境界（P9） | B1、B4 |
| 5 | 運用の体制（A3） | B2、B5 |
| 6 | 扱う個人情報と法規制、データの保管場所（P6、A7） | B1、B2、B5 |
| 7 | 利用者に与えたい印象と、参考にしたいサービス（`speckit-design` §2 の 1） | B5-1 |

- 回答は `docs/concept/core-concept.md` の末尾に「追記（日付、一括質問の回答）」の節として書き、`docs(bootstrap): 一括質問の回答をコンセプトに追記` でコミットする（trailer は付けない）。コンセプトに書くので、以降のスキルは回答を「確定」の根拠として使える。
- 再開したときに、この節がすでにあれば質問しない。
- 質問はこの 1 回だけにする。回答から新しい論点が出ても、以降は自動モードで決める。

### 各ステップでの自動の決め方

| ステップ | 論点 | 自動モードでの動作 |
|---|---|---|
| B0 | ブランチが `main`（クラウドセッションでは作業ブランチ）でない、未コミットの変更がある | 止まる（下の「止まる場面」） |
| B0 | コアコンセプトがない | 引数に追記や希望以外のテキストがあれば、それをコアコンセプトとして `core-concept.md` に書く。なければ止まる |
| B1 | ヒアリング（P1〜P10 の未決の項目） | コンセプトと競合調査から推奨案を作って採用し、状態を「確定」にする。質疑記録は `#### Q<n>（ラウンド n, auto）— <項目 ID>` とし、回答の頭に `(auto: 仮定)` を付けて、根拠（コンセプト、競合 X・Y の採用例など）を書く。調査で挙がって採否を決めない候補は、通常どおり backlog の候補にする |
| B1 | 分割案の合意 | 提示せずにそのまま書き出す。分割案は完了報告に載せる |
| B2 | ヒアリング（A1〜A9） | 根拠がなければ、小さく安く始められ、運用の手間が少なく、後から移りやすい案を採る。`docs/architecture.md` の「前提と制約」に `(auto: 仮定)` を付けて書く |
| B2 | 調査 | 省かない。Web を調べられない環境では、価格を「未調査」と書いて進め、見直しの優先度を「高」にする |
| B2 | 3 案からの選択、技術スタックの詳細 | 推奨案を採用する。比較表は `docs/architecture.md` に残す |
| B3 | 憲章の原則の確認、テストの方針 | 推奨案を採用する。テストの方針はテストファーストを既定にする。批准日など不明な日付は実行日にする |
| B4 | 共通機能の範囲、000 の分け方、書き出しの合意 | 各機能の要求から必要と判断できるものを MVP に入れ、それ以外は「後で入れる」として backlog に足す。分け方と書き出しは推奨案のまま進める |
| B5 | 目標値、CI/CD を 000 と 999 のどちらで扱うか、999 の位置、書き出しの合意 | 構成と費用で達成できる推奨値を採る。999 の位置は既定（MVP の最後）にする |
| B5-1 | ヒアリング、モックの案の選択、書き出しの合意 | `speckit-design` §6 の自動モードで決める。ブランドとトーン、主な端末は見直しの優先度を「高」にする |
| B6 | 整合の食い違い | 該当するスキルの更新モードの手順で、推奨の修正を当てる |

### 止まる場面

次の場面では自動で進めず、止まった理由とユーザーに判断してほしい事項（選択肢と推奨案）を報告して終了する。判断した後にもう一度 `speckit-bootstrap` を実行すれば（モードの指定は問わない）、続きのステップから再開する。

- B0 で、ブランチが `main`（クラウドセッションでは作業ブランチ）でない、または未コミットの変更がある
- B0 で、コアコンセプトがなく、引数にもない（`--adopt` で既存の資料をコンセプトとして扱える場合を除く）
- `--adopt` の計画で、既存のファイルを上書き・移動しないと進められない場合（§8）
- B6 の検証エラー、または B1 の `validate.py` のエラーが、3 回直しても 0 件にならない

### 記録

- 自動で決めたことは、すべて `docs/auto-decisions.md` に追記する。ステップごとに節を分け、1 件ごとに次を書く。
  - 論点、採用した案、ほかの選択肢、理由
  - 根拠の種類（コンセプト / 一括質問の回答 / 調査 / 推測）
  - 見直しの優先度（高 / 中 / 低）。予算、課金、MVP の範囲、利用者ロール、アーキテクチャの系統、根拠が推測だけのものは「高」にする
  - 反映したファイルと、見直すときに使うスキル（例: `speckit-concept-2-feature` の更新モード、`speckit-architecture` の更新モード、`speckit-nfr-feature` の更新モード、`speckit-design` の更新モード）
- 各ステップのコミットに `docs/auto-decisions.md` の更新を含める。

## 8. 取り込みモード（`--adopt`）

speckit を使っていなかった既存のプロジェクトに scaffold を取り込んだとき（`new-speckit-project adopt`）に、すでにある資料とコードを speckit の成果物に移し替えて、仕様化と実装（`speckit-all`）に入れる状態にする。**元の資料は動かさない・消さない・書き換えない。** 移し替えた成果物の冒頭には、出典の元ファイル（パスと、読んだ時点のコミット）を書く。

### 8.1 資料を探す

資料の場所はプロジェクトごとに違うので、決め打ちせずに探す。

1. `git ls-files` と、`docs/`・`doc/`・`spec/`・`design/`・ルートの `*.md` を一覧し、見出しと冒頭を読む。`node_modules/`、ビルドの出力、生成されたファイル、ベンダーのコードは読まない。
2. コードの構成（ディレクトリ、エントリーポイント、ルーティング、DB のスキーマやマイグレーション、テスト）と設定ファイル（`package.json`、`pyproject.toml`、`go.mod`、`Dockerfile`、`docker-compose.yml`、CI の設定、IaC）を読み、使っている技術と、実装済みの機能を把握する。
3. 既存の規則（取り込み前からある `CLAUDE.md`、`AGENTS.md`、`CONTRIBUTING.md`、リンターの設定など）を読む。憲章に移す候補にする。
4. 各資料を、§2 のステップの成果物の候補に当てる。綴りの揺れ（例: `docs/conpect/`）や、似た名前（`requirements.md`、`roadmap/`、`backlog`、`adr/`、`handovers/`）も候補にする。目安は次のとおり。

   | ステップ | 候補になる資料の例 |
   |---|---|
   | B0 | `README.md` の概要、企画書、提案書、`docs/concept/` |
   | B1 | 要件定義、機能一覧、ロードマップ、バックログ、Issue、実装済みのコード（画面、API、ジョブ） |
   | B2 | 設計書、ADR、`architecture*`、設定ファイル、IaC、CI の設定 |
   | B3 | 既存の `.specify/memory/constitution.md`、`CLAUDE.md` などの規則、コーディング規約 |
   | B4 | 認証・メール・権限などの共通機能のコードと設計 |
   | B5 | 性能・可用性の目標、監視・バックアップ・CI/CD の設定、運用手順書 |
   | B5-1 | デザインの資料、スタイルガイド、デザイントークン、CSS の変数、コンポーネントの一覧 |

5. 1 つの資料が複数のステップにまたがってよい（例: 1 本の設計書から B2 と B5 を作る）。

### 8.2 計画を作る

ステップごとに、次の 4 つのどれにするかを決め、根拠（候補の資料と、足りないもの）を付けて一覧にする。

| 扱い | 条件 | 動作 |
|---|---|---|
| 移し替える | 既存の資料やコードに中身があり、speckit の様式（テンプレートの見出しと表）にない | そのステップのスキルを、資料とコードを入力にして実行する。足りない項目だけを質問（自動モードでは推奨案）で埋める |
| 完了として記録 | 既存の資料がすでに speckit の成果物の場所と様式に合っている | 内容を確かめ、変更せずに §3 の形で記録する |
| 新しく作る | 候補の資料もコードもない | そのステップのスキルを通常どおり実行する |
| 飛ばす | 作っても後の工程で使わない（例: 画面のないサービスの B5-1 は「UI なし」で作るので飛ばさない。飛ばすのは、ユーザーが明示したときだけ） | 記録せず、理由を完了報告に書く。B1 と B3 は飛ばせない |

既存のものを尊重する規則:

- **B0（コンセプト）**: `docs/concept/` がなければ、`README.md` の概要や企画書から `docs/concept/core-concept.md` を作る。元の文を引用し、出典を書く。足りない点（誰の、どんな課題を、どう解決するか）は質問する（自動モードでは推奨案を仮定として書く）。
- **B1（機能）**: `speckit-concept-2-feature` の既存の実装がある場合の手順（`implementation-status.md`）で進める。実装済みの機能は、機能ファイルの状態を `実装済み（spec なし）`、一部だけなら `一部実装（spec なし）` にし、「現状の実装」節（実装済みの要求、未実装の要求、コードの場所）を書く。`speckit-worktree` の `next` は、`実装済み（spec なし）` の機能を候補にせず、`一部実装（spec なし）` の機能は候補にする（残りの要求を仕様化して実装する）。仕様を作るときは、「現状の実装」を `speckit-specify` の入力にする。
- **開発コマンド**: 既存のコードがあれば、設定ファイル（`package.json` の scripts、`Makefile`、`pyproject.toml`、CI の設定）から、テスト・リンター・型の検査・ビルドのコマンドを読み取り、`worktree_helper.py commands set` で記録する（`speckit-worktree` §4「開発コマンド」）。実際に動かして確かめ、動かないものは記録せずに完了報告に挙げる。
- **B2（アーキテクチャ）**: `speckit-architecture` の取り込みモード（§4-2）で、既存のコードと設定から現状の構成を逆起こしし、「現状を維持する案」を 3 案の 1 つにして比べる。既存の構成を変える案を採るのは、ユーザーが選んだときだけにする（自動モードでは現状を維持する）。
- **B3（憲章）**: 憲章がすでにあれば、更新モードにする。既存の規則（`CLAUDE.md` など）から移す原則と、§4 B3 の入力のうち足りない分だけを、追記の案として示す。既存の条項の番号と文言は変えない。取り込み前の `CLAUDE.md` の規則は消さず、憲章に移したものはその旨を報告する（`CLAUDE.md` から steering を読み込む行は、`new-speckit-project adopt` の案内に従ってユーザーが足す）。
- **B4・B5（000・999）**: 既存の共通機能と運用の仕組みは、`000-app-basic.md`・`999-app-nfr.md` の要求として、状態を `実装済み（spec なし）` か `一部実装（spec なし）` にして書く。予約番号 `000`・`999` が既存の機能ファイルで別の機能に使われているときは、番号を振り直さず、置き場所をユーザーに確かめる（自動モードでは止まる）。
- **B5-1（デザイン）**: 既存のスタイルやトークンがあれば、それを `docs/design/` の正本として写し、値を変えない。変えた方がよい点は「見直しの候補」に書くだけにする。
- **既存の設計判断**: 既存の資料とコードで決まっていること（言語、フレームワーク、DB、デプロイ先など）は、speckit の推奨と違っても既存を採る。変えた方がよい点は、`docs/auto-decisions.md`（対話モードでは完了報告）に「見直しの候補」として書くだけにし、勝手に変えない。
- **`.scaffold-new/`**: `new-speckit-project adopt` が衝突として置いた scaffold の版は、このスキルでは取り込まない。取り込み方は、`adopt` の案内に従ってユーザーが決める。

### 8.3 合意と実行

- **対話モード**: 計画の一覧をユーザーに示し、AskUserQuestion で確かめる（扱いを変えたいステップだけを答えてもらう形でよい。推奨は一覧のとおり）。合意した計画を `docs/adopt-plan.md`（様式: [templates/adopt-plan.md](./templates/adopt-plan.md)）に書き、`docs(bootstrap): 取り込みの計画を作成` でコミットする（trailer なし）。
- **自動モード・一括質問モード**: 計画の推奨案をそのまま採り、`docs/adopt-plan.md` と `docs/auto-decisions.md` に記録する（「完了として記録」「飛ばす」にしたステップは、見直しの優先度を「中」にする）。
- 計画のあとは、§3 の再開の規則で B1 から順に進む。「完了として記録」のステップは内容を確かめて記録だけを作り、「飛ばす」のステップは記録しない。再開したときに `docs/adopt-plan.md` があれば、計画を作り直さずにそれに従う。
- B6 の検証で、既存のファイルを書き換えないと直せないエラーが出たときは、エラーの一覧と直し方の案を完了報告に挙げ、ユーザーの合意を得てから直す（自動モードでは直さずに止まる）。

### 8.4 完了報告に足すもの

- ステップごとの扱い（移し替えた / 完了として記録した / 新しく作った / 飛ばした）と、移し替えた元の資料
- 実装済み・一部実装として記録した機能の一覧と、仕様を後から作るときの案内（`speckit-all <番号>`）
- 既存の設計判断で、speckit の推奨と違うまま残したもの（見直しの候補）
- 取り込み前の規則のうち、憲章に移したものと、`CLAUDE.md` などに残っているもの
