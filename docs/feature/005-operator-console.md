# 運営者の管理画面とお問い合わせ

**状態**: 未着手 | **区分**: MVP | **想定順序**: 5 | **依存**: 000-app-basic, 001-trademark-batch-check

## 概要

運営者が管理画面で、利用者を探して利用を停止・再開できる。利用回数の上限を変更でき、外部 API の利用件数と費用の見込みを集計で確かめられる。運営者の操作は監査ログに残る。利用者はお問い合わせフォームから運営者に連絡でき、運営者は管理画面で受け取った問い合わせを確かめられる。

## 位置づけ

無料で公開する MVP で、外部 API の費用と不正利用を抑えるための運営機能である（premises P9、docs/architecture.md §5）。運営者ロールは `000-app-basic` が、利用回数の上限の仕組みは `001-trademark-batch-check` が提供し、この機能はそれを運営者が操作できるようにする。管理画面では、個別の候補名を一切見せない（憲章 II）。

## 主な要求

- **利用者の管理**:
  - 運営者は、メールアドレスで利用者を探し、登録日、状態、今の期間の利用回数を確かめられる
  - 利用者の利用を停止・再開できる。停止の理由を記録する
  - 個別の候補名とチェックの結果は見られない
- **利用回数の上限の設定**:
  - 利用者ごとの、期間あたりの候補数の上限（既定値）を変更できる
- **外部 API の利用量**:
  - 外部サービスごとに、期間ごとの問い合わせ件数と、費用の見込みを集計で確かめられる
  - 費用の見込みが決めた水準に近づいたら、運営者に知らせる
- **監査ログ**:
  - 運営者の操作（停止・再開、上限の変更など）を、誰が・いつ・何をしたかとして記録し、一覧で確かめられる
  - 監査ログは運営者が書き換えたり消したりできない
- **お問い合わせ**:
  - 利用者は、フォームから運営者へ問い合わせを送れる（ログインしていなくても送れる）
  - 運営者は、受け取った問い合わせを管理画面で一覧でき、新しい問い合わせをメールで知らされる

主なエンティティ: 利用停止の記録、利用回数の上限の設定、外部 API の利用記録（集計用。候補名を含まない）、監査ログ、お問い合わせ

## 前提・設計原則との関係

- **共通標準**: 運営者ロールとメール送信は `000-app-basic` のものを使う。利用回数の上限は `001-trademark-batch-check` のものを使う
- **固有の制約**: 管理画面、外部 API の利用記録、監査ログに、個別の候補名を含めない（憲章 II）。問い合わせの本文に利用者が候補名を書く場合があるため、問い合わせは運営者だけが見られるようにする

## スコープ外

- 問い合わせへの返信を管理画面から送る機能（MVP では運営者が通常のメールで返信する）
- 利用者ごとに個別の上限を設ける機能、有料プラン（backlog BL-001）
- 運営者アカウントの多要素認証（backlog BL-011）
- 集計の期間、費用の通知の水準は `/speckit-clarify` と `/speckit-plan` で決める

## 根拠

- premises.md「共通基盤の候補」: 運営者向けの管理画面（利用回数の上限の設定、外部 API の利用量の確認。個別の候補名は見せない）
- premises.md Q16: ユーザーごとの回数上限を設ける
- premises.md Q21、Q22: 管理画面に、利用者の検索と停止、上限の設定、外部 API の利用量、監査ログを入れる。お問い合わせフォームを MVP に入れる
- premises.md Q23: 000 が大きくなりすぎるため、運営機能を 005 に分けた
- 区分の判断根拠: Q21・Q22 で MVP に入れると決めた。無料公開の費用を抑えるために必要
