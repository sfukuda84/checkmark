# アプリ基盤

**状態**: 未着手 | **区分**: MVP | **想定順序**: 0 | **依存**: —

## 概要

利用者が、メールアドレスとパスワード、または Google アカウントで個人アカウントを作ってログインできる。利用者は、メールアドレスの変更と退会ができ、利用規約・プライバシーポリシー・Cookie に同意したうえでサービスを使う。認証などのトランザクションメールの送信、メンテナンス中の表示、利用者と運営者を区別する仕組みも、ここで提供する。

## 位置づけ

すべての機能より先に仕様化・実装する共通基盤である。`001-trademark-batch-check` から `004-check-history` は、ここで作る個人アカウントとログインを前提にする。`005-operator-console` は、ここで作る運営者ロールを前提にする。候補名の機密性（憲章 II）は、退会時のデータの削除でも守る。

## 主な要求

- **サインアップとログイン**:
  - メールアドレスとパスワードでサインアップでき、メールアドレスの確認を終えてから使い始められる
  - Google アカウントでもサインアップ・ログインできる
  - ログアウトできる。パスワードを忘れた場合は、メールで再設定できる
  - 利用が停止されたアカウントはログインできず、その旨が示される（停止の操作は `005-operator-console`）
- **アカウント**:
  - ログインしたまま、メールアドレスを変更できる。新しいアドレスの確認を終えるまで、変更は反映されない
  - 退会できる。退会すると、本人のアカウント情報、チェック、候補名、結果がすべて削除される。退会の前に確認する
- **同意**:
  - サインアップの時に、利用規約とプライバシーポリシーへ同意する。利用規約には、結果が「簡易チェック」であって法的判断ではないことを含める
  - 規約が改定されたら、次のログインの時に改めて同意を求める。どの版にいつ同意したかの履歴を残す
  - 初回の訪問時に Cookie の利用への同意を求め、必須でない Cookie は同意するまで使わない
- **トランザクションメール**:
  - メールアドレスの確認、パスワードの再設定、メールアドレスの変更の確認を、利用者にメールで送る
- **利用者と運営者の区別**:
  - アカウントには「利用者」か「運営者」のロールがあり、運営者だけが運営者向けの画面に入れる（画面の中身は `005-operator-console`）
- **メンテナンス表示**:
  - 更新作業や商標データの取り込みでサービスを止めている間は、利用者にメンテナンス中であることを示す

主なエンティティ: アカウント（ロール、状態＝有効／停止を持つ）、ログイン手段（メールとパスワード、Google）、セッション、同意の履歴（規約の版ごと）

## 前提・設計原則との関係

- **共通標準**: 認証は Better Auth で行い、セッションは自前の PostgreSQL に持つ（docs/architecture.md §3）。メールは Resend で送る（docs/architecture.md §3）
- **固有の制約**: 退会時の削除は憲章 II（候補名の機密性）に従い、アプリの DB から復元できない形で消す。バックアップに残る期間は `docs/nfr.md` に定める。運営者であっても、利用者のパスワードや個別の候補名は見られない

## スコープ外

- 運営者向けの管理画面の中身（利用者の検索と停止、上限の設定、利用量、監査ログ）とお問い合わせフォーム（`005-operator-console` が扱う）
- 多要素認証（backlog BL-011）
- パスキー、マジックリンク（backlog BL-012）
- 組織（Workspace）とメンバーの招待（backlog BL-002）
- 有料プランと決済（backlog BL-001）
- パスワードの強度の条件、セッションの有効期間、確認メールのリンクの有効期間は `/speckit-clarify` と `/speckit-plan` で決める

## 根拠

- premises.md「共通基盤の候補」: 個人アカウントの登録とログイン、退会、メール送信、利用規約への同意
- premises.md Q4: 個人アカウントで履歴を保存する
- premises.md Q11: 候補名は本人だけが閲覧・削除できる
- premises.md Q19〜Q22: ログインはメールとパスワード、Google。多要素認証は後で入れる。メールアドレスの変更、メンテナンス表示、Cookie の同意を MVP に入れる
- docs/architecture.md §3: Better Auth、Resend
- 区分の判断根拠: MVP のすべての機能がログインを前提にする
